# GBE3 通信协议实现检查报告

## 1. 检查范围

- 固件分支：`hsf`
- 公共协议：`260820_GB_common_communication_protocol_Baseline1.0.docx`
- GBE3协议：`260903_GBE3_communication_protocol_binary_Rev2.3(2).docx`
- 主要代码：`protocol/gb_protocol.c`、`protocol/gbe_protocol.c`、`src/usb_cdc.c`、`src/usb_prop.c`、`bsp/bsp_ir.c`、`src/main.c`
- 修改后编译结果：Keil ARMCC 5.06，0 Error；6个原有未使用变量Warning

本次只进行了代码和协议检查，没有修改固件功能。

## 2. 当前完成情况

协议规定的命令均已有对应实现，暂未发现缺少整条命令：

| 功能 | 命令 | 当前状态 |
| --- | --- | --- |
| 握手 | `0x0001 / 0x1001 / 0x3001` | 已实现 |
| 环境光通知 | `0x2301` | 已实现 |
| 运动传感器通知 | `0x2302` | 已实现 |
| 运动传感器状态查询 | `0x0303 / 0x1303 / 0x3303` | 已实现 |
| 红外接收通知 | `0x2401` | 已实现NEC、AEHA、Sony |
| 红外发射 | `0x0402 / 0x1402 / 0x3402` | 已实现NEC、AEHA、Sony及Repeat |

HID键盘属于通信协议以外的附加USB功能，本报告不把它计入协议缺项。

## 3. 待处理问题

### 3.1 Critical

#### 3.1.1 发送帧缓冲区边界（已处理）

位置：`protocol/gb_protocol.c`，`Protocol_SendFrame()`。

```c
uint8_t tx_buf[500] = {0};
memcpy(&tx_buf[8], payload, payload_len);
```

接收方向继续支持协议规定的2048字节Payload。发送方向根据当前命令限制为164字节，这是最大AEHA接收通知的Payload长度。

`Protocol_SendFrame()`的发送数组已经调整为174字节，并在复制前检查`payload_len <= 164`，避免越界。

建议：

- 后续如果新增Payload超过164字节的Device到Host命令，需要同步调整发送上限。
- 如果未来要求Device到Host完整支持2048字节Payload，应重新设计分段组帧，不能直接新增大数组。

#### 3.1.2 等待USB配置可能永久阻塞（已处理）

位置：`src/main.c`，`main()`。

```c
while (bDeviceState != CONFIGURED)
{
}
```

启动时等待`CONFIGURED`的死循环已经删除。没有连接电脑或枚举失败时，PIR、环境光和红外模块仍会继续初始化；USB未配置时底层收发接口自行拒绝传输。

后续需要在未连接USB、延迟枚举和枚举失败三种情况下分别做上电测试。

### 3.2 High

#### 3.2.1 USB重连没有重置协议会话（USB Reset路径已处理）

位置：`src/usb_prop.c`，`Virtual_Com_Port_Reset()`。

`USB_CDC_Reset()`现在支持注册Reset回调。`gbe_protocol_init()`注册协议会话重置函数后，每次USB总线Reset都会同步清理：

- 协议接收状态机；
- `SessionState`；
- Notification Sequence；
- `g_ir_tx.pending`及旧请求Sequence。

CDC的收发队列由`USB_CDC_Reset()`清空，正在执行的物理红外发射允许继续完成，但不会再向新会话发送旧请求的响应。

COM关闭路径仍需单独处理，见下一项。

#### 3.2.2 COM口关闭没有结束会话

位置：`src/usb_prop.c`，`Virtual_Com_Port_NoData_Setup()`。

收到CDC `SET_CONTROL_LINE_STATE` 后直接返回成功，没有保存DTR状态，因此无法利用DTR清零识别上位机关闭COM口。

建议：记录DTR状态，在检测到端口关闭时终止协议会话；重新打开后必须重新握手。

#### 3.2.3 红外发送缺少超时恢复

位置：`bsp/bsp_ir.c`，`IR_TransmitPoll()`；`protocol/gbe_protocol.c`，`gbe_protocol_ir_response_poll()`。

如果TIM6中断或红外发送状态机异常，`is_sending`可能永远不能清零，`g_ir_tx.pending`也会一直保留。之后所有红外请求都会返回Busy。

建议：

- 按协议、位数和Repeat计算合理的最大执行时间；
- 超时后停止TIM6和PWM并恢复红外状态机；
- 向当前请求返回Internal Error；
- 清除`pending`，确保后续请求可以继续执行。

#### 3.2.4 红外参数校验不完整

位置：`protocol/gbe_protocol.c`，`gbe_protocol_pc_request_ir_tansimit()`。

当前问题：

- NEC的`Repeat Count = 0`返回Invalid Payload，协议要求返回Invalid Parameter；
- Sony没有提前拒绝`Repeat Count = 0`，可能实际发送一帧后再返回Internal Error；
- Sony Data的bit7没有校验，而是被静默清除；
- AEHA Data Bit Count不是8的倍数时，没有检查最后一个数据字节的未使用高位是否为0；
- 多数Invalid Parameter的Error Detail固定为0，没有填写错误字段的0基索引；
- 多数Invalid Payload Size的Error Detail没有填写期望长度或允许的最大值。

建议：在启动物理发射前完成全部校验，参数错误时不能产生任何红外输出。

#### 3.2.5 Repeat Count与10秒响应超时冲突

GBE3协议同时规定：

- Repeat Count允许1至255；
- 正常响应必须等所有物理发射完成；
- IR Transmission Response Timeout固定为10秒。

当前时序下：

- NEC发送255次约需27秒；
- Sony发送255次约需11.5秒；
- 长数据AEHA发送255次可能远超10秒。

这三个要求无法同时满足，属于协议本身需要确认的事项。

建议二选一：

1. 根据协议和Data Bit Count限制Repeat Count，确保10秒内完成；
2. 保留1至255范围，将响应超时改成可计算的命令相关超时。

### 3.3 Medium

#### 3.3.1 Host Max Payload没有参与发送限制

位置：`protocol/gb_protocol.c`，`Handle_Handshake()`。

固件读取并打印了`Host Max Payload Size`，但没有保存，也没有限制Device到Host方向的Payload。

协议要求：

```text
Device -> Host = min(2048, Host Max Payload Size)
```

建议：握手成功时保存协商值，所有Response和Notification入队前统一检查。

#### 3.3.2 Response发送失败可能造成主机超时

例如运动状态查询调用`gb_protocol_send_response()`后没有检查返回值。CDC发送队列满时，请求可能没有任何响应。

建议：Response和Error Response应具有独立的待发送状态；入队失败时保留请求并优先重试，不能直接丢弃。

#### 3.3.3 发送优先级没有完全落实

`gbe_protocol_poll()`会先处理红外完成响应，再生成普通Notification，但CDC底层只有一个FIFO字节队列，无法区分Response和Notification，也无法丢弃新会话开始前尚未发送的Notification。

建议：在协议层分别管理高优先级响应和普通通知，再按以下顺序提交CDC：

```text
Response / Error Response > Notification
```

#### 3.3.4 红外发射期间可能收到自身红外信号

红外接收捕获在发射期间仍然运行。如果接收头能看到本机红外LED，可能将自身发射内容解码并产生`0x2401`通知。

建议：结合硬件实测决定是否在发射期间屏蔽接收通知，或在发送完成后丢弃对应回波窗口内的数据。

#### 3.3.5 RAM余量较小

目标器件RAM为24KB。当前链接布局的RAM上限已经到`0x20005AF8`，距离`0x20006000`只剩约1288字节未分配。

主要占用包括：

- 两个红外捕获缓冲区；
- USB CDC收发环形缓冲区；
- 2058字节协议接收缓冲区；
- 5.25KB栈和768字节堆。

建议：修复最大帧发送时先评估RAM，不要直接新增2KB以上全局发送数组。

## 4. 文档待确认项

1. 文件名标记为`Rev2.3`，但文档正文修订记录最高为`2.2`，应确认正式版本号。
2. AEHA Data Bit Count在代码中限制为28至1260，但协议没有明确写出允许范围，需要在协议中固定。
3. 环境光传感器最终有效测量范围仍是协议Open Item。
4. USB麦克风48kHz/16bit格式仍是协议Open Item，由最终硬件规格确认。

## 5. 建议处理顺序

1. 增加协议会话重置接口，并接入USB Reset和COM关闭路径。
2. 补全NEC、AEHA、Sony参数校验及Error Detail。
3. 增加红外发送超时、停止和状态恢复路径。
4. 解决`Protocol_SendFrame()`长度检查和发送缓冲区边界。
5. 明确Repeat Count与10秒响应超时的最终协议规则。
6. 完善Response重试、发送优先级及握手协商Payload限制。
7. 做断线重连、队列满、最大Repeat和异常中断压力测试。

## 6. 建议验证项目

- USB未连接上电，确认主程序不会永久卡住。
- 完成握手后触发USB Reset，确认Notification停止并要求重新握手。
- 关闭、重新打开COM口，确认必须重新握手。
- 在红外发射中途模拟TIM6不再运行，确认能够超时恢复且下一条请求可执行。
- 分别测试三种红外格式的Repeat Count为0、1、最大值和非法字段。
- 测试AEHA非8倍数Data Bit Count及最后一字节非法高位。
- 人为填满CDC发送队列，确认Response不丢失且优先于Notification。
- 对最大合法接收帧、超长Payload、CRC错误、字节超时和整帧超时进行压力测试。
